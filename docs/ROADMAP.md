## アプリの目的

ファゴット(バスーン)のフィンガリング(運指)を記録し、シェアするためのアプリ。

1. 音名とそのフィンガリングを簡単に記録できる
2. 記録したフィンガリングをスマホやSNSで簡単にシェアできる
3. 個人的に永続保存・参照できる
4. (将来)GitHubのように全世界の人と共有・蓄積・改善できる

2026-07-11 時点の Fable の推奨: **Web版(本リポジトリ)への一本化を推奨**(前回判断の逆転)。理由:

1. 機能2〜4はいずれも「URLを開けば誰でも見られる」ことが本質で、Webの受け皿はどのみち必須。Web一本ならコードベース1つで全機能を賄える。
2. App Store の制約(Sign in with Apple 必須、UGCの通報・ブロック機能必須、審査、bundleIdentifier)をすべて回避できる。
3. ビルド無しの Vanilla JS 静的サイトは、独学レベルの作者が AI 支援で保守するのに最も容易な構成。Expo/React Native はネイティブビルドの複雑さが加わる。
4. 資産の比較: Web版には完成度の高い運指図SVG・シェアUX・五線譜表示がある。Expo版の進捗(SQLite CRUD・エクスポート)は「概念」として Web版の Phase 1 に移植しやすい。
5. Web版の弱点は iOS Safari のローカルストレージ揮発性(しばらく使わないと消されることがある)→ JSONエクスポート/インポート(Phase 1)とクラウドアカウント(Phase 4)で緩和できる。

ただし最終判断は作者が行う。Expo版を選ぶ場合でも、**Phase 0(KEYMAP確定+SVGへのID付与+スキーマv1)は、Expo版へのSVG移植でもID付与が前提になるため、どちらの道でも無駄にならない**。先に進めてよい。
決定後、選ばなかった側のリポジトリの README に「開発は◯◯版に一本化した」と書いてアーカイブすること。

## データスキーマ v1(Expo版と共通仕様。全フェーズの土台)

Phase 0 で確定させ、以後 localStorage・シェアURL・クラウドDB すべてでこの形を使う。

```json
{
  "version": 1,
  "note": "C#4",
  "trillNote": "D#4",
  "keys": {
    "whisper": 1,
    "hole1": 2,
    "cs-trill": 3
  },
  "label": "ピアニッシモ用の替え指",
  "createdAt": "2026-07-11T00:00:00Z"
}
```

- `note`: 音名。`C#4` / `Bb2` のように「音名+臨時記号+オクターブ番号」(国際式)。音名リストの唯一の正を `lib/notes.js`(仮称)に定数として定義する(Expo版の `types.ts` の `NOTES` に相当)。
- `keys`: キーID → 状態のマップ。**0=開放(無色), 1=押す(黒), 2=半開・特殊(青), 3=トリル対象キー(赤)**。値0のキーは省略可(スパース表現)。
  - ⚠️ **Expo版 ROADMAP のスキーマは 0|1|2 のみ**(2=特殊・半開)。本Web版のUIには「赤=トリルキー」の状態が既に実装されているため、**値3の追加を提案する**。0〜2 の意味は Expo版と同一のまま追加するだけなので後方互換。**作者の承認を取り、承認されたら Expo版 `docs/ROADMAP.md` にも反映して両文書を一致させること。**
- `trillNote`: トリル相手の音名(任意項目。Web版のトリル音選択UIに対応)。これも Expo版仕様への追加提案。同様に作者確認のうえ両文書へ反映。
- `version`: スキーマ変更に備えて必ず持つ(エクスポートJSON・シェアURLに含める)。
- `label`: 用途メモ(現行のメモ機能をこのフィールドに載せ替える)。

### シェアURL形式(Expo版と共通仕様)

```
https://<host>/?v=1&n=Cs4&k=whisper.1_hole1.2
トリル時: ...&tn=Ds4 (トリルキーは k の中の値3で表す)
メモ時:   ...&l=%E6%9B%BF%E3%81%88%E6%8C%87 (URLエンコード)
```

- 音名の `#` はURLと衝突するため `s`、`♭` は `b` で表す(`Cs4`, `Bb2`)。
- クエリパラメータ形式(Expo版のディープリンク `bassoonfingering://f?...` と互換にするため。ハッシュ形式は使わない)。
- パースとシリアライズは `lib/shareUrl.js` として副作用のない純関数で実装し、`node` で単体実行できるテストを付ける(`npm test`)。
- **メモ(`label`)は `l` に含める(2026-07-27決定)。** 当初は「長文になりうる」ため保留していたが、LINE等が画像+テキスト共有時にテキストを捨てる場合があり、メモが相手に届かない問題があったため方針転換した。
  - 上限は200文字(`SHARE_URL_LABEL_MAX_LENGTH`)。超過分は切り詰めて末尾に `…` を付ける。**アプリ内のメモ本体は切らず、URL化する時だけ縮める。**
  - 日本語は1文字がURL上9バイトに膨らむため、200文字で約1800バイト。URL全体で約1900文字に収まる(実測1865文字)。
  - `l` は任意パラメータで、無くても従来どおり読める(`label: ''` になる)。**後方互換のため `version` は 1 のまま据え置く**(`trillNote` を追加した時と同じ考え方)。
  - ⚠️ メモがURLに載るため、ブラウザ履歴・チャットのリンクプレビュー・サーバーのアクセスログに残る。機微な内容を書く用途には向かない旨をUIで案内するかは今後の検討事項。

### キーID(KEYMAP)

`picture/bassoon_key.svg` には形状が30個あり、うち2個は区切り線(y=250 の水平 line と x=229 の縦 path)。**キー本体は28形状**。現状すべて id 無し。

Phase 0 で全キー形状に id を付与し、`docs/KEYMAP.md` に「id ↔ キー名称(日/英) ↔ SVG内のおおよその位置」の対応表を記録する。id の候補は Expo版 ROADMAP の草案(`whisper`, `hole1`〜`hole6`, `low-c`, `bb-pancake` 等)をそのまま使う。

**どの形状がどのキーかは、ファゴット奏者である作者に1つずつ確認して確定する。AIの楽器知識で推測して確定させないこと。**(SVGは区切り線で4象限に分かれており、手・親指の別と推測されるが、これも作者確認)

確認の進め方の例: 一時的に各形状へ通し番号を色付き表示するデバッグモードを作り、作者に「1番は何のキーですか」と順に聞いて表を埋めるのが確実で速い。

## Phase 4: 共有プラットフォームMVP(機能4 前半)

**技術選定: Supabase(Auth + PostgreSQL + Row Level Security)。**
選定理由は Expo版 ROADMAP と同じ(無料枠が個人開発に十分、認証とDBが一体、音名検索・人気順がSQLで素直、情報が豊富で Opus/Sonnet でも実装知見が安定)。静的サイトからは `@supabase/supabase-js` を ESM CDN(esm.sh 等)で読み込めばビルド無しのまま使える。anon キーは公開前提の設計なので静的サイトに直書きしてよい(データ保護はRLSで行う)。

### 投稿データのライセンス方針(2026-07-28決定・実装はPhase 4着手時)

**アプリ本体(コード)のライセンスと、ユーザーが投稿する運指データのライセンスは別に考える。**

- アプリ本体(`app.js`・`picture/bassoon_key.svg` 等): **CC BY-NC 4.0**(表示・非営利)。商用利用には作者の許可が必要(`LICENSE`参照)。
- **投稿された運指データ: CC BY-SA 4.0(表示・継承)を想定。** 作者の意向は「プロ・アマ問わずファゴット奏者間で幅広く共有し、共通の財産にしたい」ため、コードとは逆に**非営利の縛りを付けない**。BY-SAにすることで、誰かがコミュニティの投稿データを大量に取り込んで自社サービスに囲い込む(データだけ吸い上げて非公開の派生物にする)ことを防ぎつつ、自由な二次利用・再配布を許す。
- 投稿者名の表示は法的な話ではなく**アプリの機能**として実現する(上記 `fingerings` テーブルの `author_id` を画面に出すだけ)。CC BY-SAの「表示(Attribution)」条件は、アプリの外(誰かがAPI経由で取得し別サイトへ転載する等)でもクレジット表示義務が法的に効力を持つための担保。
- Phase 4着手時に必要な実務対応: **投稿フォーム付近に「投稿するとCC BY-SA 4.0で公開されることに同意したものとします」等の利用規約(ToS)の一文を明記する。** 投稿時の同意が、運営側がユーザー投稿をCC BY-SAで再配布してよい法的根拠になる(Wikipedia・Stack Overflow等と同じ考え方)。

MVPスコープ(この順に実装):
1. Supabase プロジェクト作成。ログインは**メールのマジックリンクのみ**から始める(Web版は App Store 審査が無いので Sign in with Apple の必須要件も無い。ソーシャルログインは後から足せる)。
2. `fingerings` テーブル: `id, author_id, note, trill_note, keys jsonb, label, description, forked_from, created_at`。RLSは「読み取りは全員、書き込み・更新・削除は本人のみ」。
3. 投稿: ライブラリの運指を公開投稿(ローカル=下書き、Supabase=公開版という関係)。
4. 一覧・検索: 音名で検索、新着順。閲覧はログイン不要。
5. いいね: `likes` テーブル(`user_id, fingering_id` ユニーク制約)。人気順ソート。
6. 取り込み: 他人の投稿を自分のローカルライブラリへ保存。

やらないこと(Phase 5 に送る): コメント、フォークUI、編集履歴、通報・モデレーション。

完了条件: 他人が投稿した運指を音名で検索して開き、自分のライブラリに取り込める。

## Phase 5: GitHub的な改善サイクル(機能4 後半)

1. **フォーク**: 「この運指を元に改変して投稿」。実装は `forked_from` に親IDを入れた新規投稿にするだけ。派生ツリーを投稿詳細に表示。
2. **差分表示**: 親と子の `keys` マップを比較し、変わったキーを運指図上でハイライト(スキーマv1なら単純なオブジェクト比較で済む)。
3. **コメント**: `comments` テーブル。
4. 通報・削除(モデレーション)。Web のみなら Apple 審査要件は無いが、公開プラットフォームの運営者としての責務として必要。

## 引き継ぎ時の注意(Opus / Sonnet へ)

- 作者はファゴット奏者。エンジニア経験は独学レベル。専門用語は補足しながら、日本語・敬語で、結論から伝えること。
- **KEYMAP(キーID一覧)とSVG形状の対応付けは、ファゴット奏者である作者の確認が必須。** AIの楽器知識だけで確定させない。
- スキーマを変えるときは必ず `version` を上げ、旧バージョンの読み込み互換を残す(シェアURLやエクスポートJSONが古い形式で出回るため)。
- Expo版リポジトリ(`~/dev/bassoon-fingering`)の `docs/ROADMAP.md` と本文書は、スキーマ・シェアURL仕様を常に一致させる。片方だけ変えないこと。
- **ビルド無し・Vanilla JS 構成を維持する。** フレームワークやバンドラの導入は作者の保守コストに合わないため、明確な理由なく提案しない。ファイル分割は `<script type="module">` の範囲で行う。
- 依存追加は最小限: Phase 4 の supabase-js(CDN経由)のみ想定。それ以外の追加は理由を明記すること。
