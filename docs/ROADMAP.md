# Bassoon Key App — 改善ロードマップ

作成日: 2026-07-07(Claude Fable 5 によるコードレビューに基づく)
このドキュメントは、Claude(Opus / Sonnet 等)や他の開発者が引き継いで実装できるように書かれている。
実装を依頼するときは「docs/ROADMAP.md の Phase X を実装して」と指示すればよい。

---

## アプリの目的

ファゴット(バスーン)のフィンガリング(運指)を記録し、シェアするためのアプリ。

1. 音名とそのフィンガリングを簡単に記録できる
2. 記録したフィンガリングをスマホやSNSで簡単にシェアできる
3. (将来)個人的に永続保存・参照できる
4. (将来)GitHubのように全世界の人と共有・蓄積・改善できる

## 現状(2026-07-07 時点)

- 構成: 静的サイト。`index.html` + `app.js` + `app.css` + `picture/bassoon_key.svg`。フレームワークなし(Vanilla JS)。
- 動作: SVGを fetch してインライン挿入し、キー(path)をクリックすると fill が black → red → white とサイクルする。「Fingering Download」ボタンで表示中のSVGをPNG化してダウンロードする。
- **最重要の問題: `picture/bassoon_key.svg` の30個の `<path>` に `id` が一つもない。**
  そのため運指を「どのキーが押されているか」というデータとして表現できず、画像としてしか残せない。
  保存(機能3)・共有(機能4)はすべて「運指のデータ化」が前提なので、これが全フェーズのブロッカー。
- 音名(ノート名)を入力・記録するUIが存在しない。
- PNG書き出しは `getBoundingClientRect()` の表示サイズでラスタライズしており、スマホでは低解像度(〜350px幅)になる。
- `app.js` 冒頭の `#circle` を扱うIIFE(1〜11行)は旧実装の名残で、現在のSVGに `#circle` は存在しない。削除してよい。

## データスキーマ v1(全フェーズ共通の土台)

Phase 0 で確定させ、以後 localStorage・URL・クラウドDB すべてでこの形を使う。

```json
{
  "version": 1,
  "note": "C#4",
  "keys": {
    "whisper": 1,
    "hole1": 1,
    "hole2": 0
  },
  "label": "ピアニッシモ用の替え指",
  "createdAt": "2026-07-07T00:00:00Z"
}
```

- `note`: 音名。表記は `C#4` / `Bb2` のように「音名+臨時記号+オクターブ番号」(国際式)。UI上はドイツ音名併記も検討。
- `keys`: キーID → 状態。状態は整数で `0=開放(white)` `1=押す(black)` `2=特殊/半開(red)`。値が0のキーは省略してよい(スパース表現)。
- `version`: スキーマ変更に備えて必ず持つ。
- キーIDの正式な一覧は Phase 0 で `docs/KEYMAP.md` として作成すること。

### URLエンコード形式(Phase 1)

サーバー不要のシェアを実現するため、状態をURLハッシュに載せる:

```
https://<host>/#v=1&n=Cs4&k=whisper.1_hole1.1_hole3.2
```

- `#` 以降なのでサーバーログに残らず、GitHub Pages のままで動く。
- 音名の `#` は URL と衝突するので `s`(sharp)、`♭` は `b` で表す(`Cs4`, `Bb2`)。
- ページ読み込み時にハッシュをパースして運指を復元する。操作のたびに `history.replaceState` でハッシュを更新すれば、「今見ている状態のURLをコピーするだけ」でシェアできる。

## Phase 0: 運指のデータ化(すべての前提。最初にやる)

**目的: 運指を画像ではなくデータとして扱えるようにする。**

1. `picture/bassoon_key.svg` の30個の `<path>` それぞれに `id` を付与する。
   - 命名は実際のファゴットのキー名に基づく(例: `whisper`, `hole1`〜`hole6`, `low-bb`, `low-b`, `low-c`, `low-d`, `c-sharp`, `f-key`, `a-flat`, `f-sharp`, `high-a`, `high-c`, `high-d` など)。
   - **どのpathがどのキーかはSVGを目視しないと分からないため、ブラウザで1つずつクリックして特定するか、ユーザー(作者)に確認しながら進めること。** 楽器の絵の輪郭など「キーではない装飾パス」には `data-decoration` を付けてクリック対象から除外する。
2. キーIDと日本語名・役割の対応表を `docs/KEYMAP.md` に残す。
3. `app.js` に状態管理を導入する: DOM の fill 属性を直接読むのではなく、`state = { note, keys: {...} }` を単一のソースとして持ち、描画はそこから反映する(保存・URL復元・リセットが全部これに乗る)。
4. クリック対象を `id` 付きのキーpathに限定する(`data-decoration` は無視)。

完了条件: 任意の運指が JSON(上記スキーマ)で取り出せ、JSON から画面を復元できる。

## Phase 1: 記録・シェア体験の改善(機能1・2)

Phase 0 完了後、以下を実装する。独立性が高いので1項目ずつ進めてよい。

1. **URLシェア**: 上記URLエンコード形式の実装。「リンクをコピー」ボタンを追加。
2. **音名セレクタ**: 音名(A#1〜E5程度、♯/♭両表記)を選ぶUI。選んだ音名は書き出し画像の中に描画し、ファイル名にも反映(`fingering_Cs4.png`)。
3. **高解像度PNG書き出し**: `getBoundingClientRect()` ではなく viewBox(619×956)×2倍の固定サイズでラスタライズする。画像内に音名・凡例・アプリURLを焼き込む。
4. **Web Share API**: `navigator.share({ files, url })` が使える環境ではネイティブ共有シートを開く(スマホでのSNSシェアがワンタップになる)。非対応環境は従来のダウンロードにフォールバック。
5. **凡例とリセット**: 黒=押す/赤=特殊/白=開放の凡例を画面に常時表示。「全リセット」ボタン追加。
6. **タップ精度の改善**: 細いstrokeパスはスマホで押しにくい。各キーpathの背後に同じ形で `stroke-width` を太くした透明のヒット用pathを複製配置する(クリックイベントは本体キーに委譲)。
7. 旧 `#circle` 用IIFE(app.js 1〜11行)の削除。
8. OGPメタタグ(`og:title`, `og:image` 等)の追加。

完了条件: スマホで運指を作り、URLまたは画像をLINE/Xにワンタップでシェアでき、受け取った側がURLから同じ運指を開ける。

## Phase 2: 個人の永続保存(機能3)

**localStorage で実装する。サーバー・アカウント不要、無料、実装量も小さい。**

1. 「保存」ボタン: 現在の state(スキーマv1 + label)を localStorage のリスト(キー例: `bassoon-fingerings`)に追加。
2. 「マイライブラリ」画面(同一ページ内のパネルでよい): 保存済み運指の一覧(音名・ラベル・日時)、タップで復元、削除。
3. JSONファイルでのエクスポート/インポート(機種変更・バックアップ対策。localStorageはブラウザ消去で消えるため必須)。
4. 音名での絞り込み(件数が増えたとき用)。

端末間同期はここではやらない。Phase 3 のバックエンドに乗せる方が二度手間にならない。

完了条件: ブラウザを閉じても保存した運指一覧が残り、JSONで書き出し・読み込みできる。

## Phase 3: 共有プラットフォームMVP(機能4 前半)

**技術選定: Supabase(Auth + PostgreSQL + Row Level Security)+ 既存の静的ホスティング。**

選定理由(2026-07-07 時点の判断。引き継ぎ時に代替があれば再検討可):
- 無料枠が個人開発に十分で、認証とDBが一体。
- 音名検索・人気順ソートがSQLで素直に書ける(FirebaseのNoSQLより検索要件に合う)。
- 情報が豊富で、Claude(Opus/Sonnet)でも実装知見が安定している。
- フロントは静的サイトのままでよく、既存構成を壊さない。

MVPスコープ(この順に実装):
1. Supabase プロジェクト作成、Googleログイン(Supabase Auth)。
2. `fingerings` テーブル: `id, author_id, note, keys(jsonb), label, description, created_at`。RLSは「読み取りは全員、書き込みは本人のみ」。
3. 投稿機能: ローカルの運指を公開投稿する。
4. 一覧・検索: 音名で検索、新着順。
5. いいね: `likes` テーブル(`user_id, fingering_id` のユニーク制約)。人気順ソート。

やらないこと(Phase 4 に送る): コメント、フォーク、編集履歴、通報・モデレーション。

完了条件: 他人が投稿した運指を音名で検索して開き、自分のライブラリに取り込める。

## Phase 4: GitHub的な改善サイクル(機能4 後半)

1. **フォーク**: 「この運指を元に改変して投稿」。実装は `parent_id` カラムを持つ新規投稿にするだけでよい。派生ツリーを投稿詳細に表示。
2. **差分表示**: 親と子の `keys` を比較し、変わったキーをSVG上でハイライト(データがJSONなので単純比較で済む)。
3. **コメント**: `comments` テーブル。
4. モデレーション(通報、削除)— 公開プラットフォーム化するなら必須。

## 引き継ぎ時の注意

- **Phase 0 のキーID命名だけは、ファゴット奏者である作者の確認が必須。** SVGのどのpathがどのキーに対応するかはコードからは判別できない。
- 現状はビルド工程なし・依存ゼロ。Phase 3 までこの方針を維持する(SupabaseもCDNのJSクライアントで足りる)。フレームワーク導入はUIが本当に複雑になってから検討する。
- スキーマを変えるときは必ず `version` を上げ、旧バージョンの読み込み互換を残すこと(URLやエクスポートJSONが古い形式で出回るため)。
- ホスティングは GitHub Pages を想定(リポジトリ名からの推定)。デプロイ先が変わったらこの節を更新すること。
